Undoing changes

Git offers a safe way back at every stage, and choosing the right undo command depends on where your mistake lives.

11.1 First, where is the mistake

Git has several undo commands because a mistake can live in three different places. Find the place first, then pick the command.

Where the mistake isWhat it looks likeCommand
Working directoryYou edited a file and want the old version backgit restore <file>
Staging areaYou staged a file by mistakegit restore --staged <file>
Last commit (not shared)Wrong message or a forgotten filegit commit --amend
Last commits (not shared)You want to redo recent commitsgit reset
Shared commitSomeone else already has the commitgit revert <commit>

11.2 Discard changes in the working directory

$ git restore README.md

The file returns to its last committed (or staged) state.

Caution

This cannot be undone. Your unsaved edits are gone, because Git never recorded them.

11.3 Unstage a file

$ git add secret.txt
$ git restore --staged secret.txt

The file leaves the staging area, but your edits stay in the working directory.

11.4 git reset: move the branch back

git reset moves the current branch to an earlier commit. The three modes decide how much of your work is also reset.

ModeBranch movesStaging areaWorking directory
--softYesKeptKept
--mixed (default)YesClearedKept
--hardYesClearedCleared
 
$ git reset --soft HEAD~1
$ git reset HEAD~1
$ git reset --hard HEAD~1
  • Use --soft to redo a commit: your changes stay staged, ready to commit again.
  • Use --mixed to unstage and rethink.
  • Use --hard only when you truly want to throw the work away.
Caution

git reset --hard destroys uncommitted work. Check git status first.

11.5 git revert: undo safely in shared history

Reset rewrites history, which is dangerous once others have your commits. Revert adds a new commit that cancels an old one, so history is never rewritten.

$ git revert 3f2a9c1
[main 7b1d2e4] Revert "Add login"
 1 file changed, 5 deletions(-)

Use revert for anything that has been pushed to a shared branch.

11.6 git clean: remove untracked files

$ git clean -n
Would remove debug.log
$ git clean -f
Removing debug.log

Always run -n (dry run) first. Add -d to include untracked folders.

11.7 Decision guide

  • Not committed yet: restore.
  • Committed but not pushed: reset or --amend.
  • Pushed and shared: revert.
Tip

If you reset too far, the commits are not gone yet. Chapter 35 shows how git reflog finds them again.

11.8 Common mistakes

  • Using reset --hard casually. Prefer --soft or --mixed.
  • Resetting a shared branch and force-pushing. This breaks everyone else's history. Use revert.
  • Confusing restore with revert. Restore changes files; revert creates a commit.
Quick recap
  • git restore discards working changes; git restore --staged unstages.
  • git reset moves the branch; --soft, --mixed and --hard decide how much is reset.
  • git revert safely cancels a commit by adding a new one.
  • Use revert for shared history, reset only for local history.
Check yourself

1. A commit has already been pushed to the shared main branch and is wrong. What is safest?

Revert adds a new commit and does not rewrite shared history.

2. Which command unstages a file but keeps your edits?

Practice exercise
  • Edit a file, then discard the edit with git restore.
  • Stage a file, then unstage it with git restore --staged.
  • Make two commits, run git reset --soft HEAD~1, and see the changes staged again.
  • Make a commit and undo it with git revert. Look at git log --oneline.
