Cherry-pick

Cherry-pick copies a single commit from one branch onto another without merging everything else.

18.1 When you need it

Imagine a bug fix was committed on a feature branch, and the same fix is needed urgently on main, but the rest of the feature is not ready. Cherry-pick takes just that one commit.

18.2 The command

$ git switch main
$ git cherry-pick 8e4c1b7
[main a3b9d21] Fix null pointer crash
 1 file changed, 2 insertions(+)

The copy has a new hash, because it has a new parent.

CommandResult
git cherry-pick <hash>Copy one commit
git cherry-pick A B CCopy several commits
git cherry-pick A..BCopy the range after A up to B
git cherry-pick -x <hash>Add a note saying where it came from
git cherry-pick -n <hash>Apply the change but do not commit

18.3 Conflicts

If the change does not apply cleanly, Git stops. Resolve the files, then run:

$ git add file.py
$ git cherry-pick --continue
$ git cherry-pick --abort

18.4 When to use it, and when not to

  • Good for hotfixes that must reach a release branch quickly.
  • Good for rescuing one useful commit from an abandoned branch.
  • Poor as a routine way to move work. Duplicate commits make history confusing, and you may see the same change twice when the branches are merged later.

18.5 Common mistakes

  • Cherry-picking too much. If you need many commits, merge or rebase instead.
  • Forgetting the original still exists. The source branch keeps its own copy.
Quick recap
  • Cherry-pick copies selected commits to the current branch.
  • The copies get new hashes.
  • Use -x to record the source commit.
  • Resolve conflicts, then --continue.
