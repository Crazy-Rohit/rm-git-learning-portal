Tags

A tag is a permanent name for one commit, usually used to mark a release such as version 1.0.

20.1 Branches move, tags stay

A branch name follows new commits. A tag always points to the same commit, which makes it ideal for marking releases like v1.0.0.

20.2 Two kinds of tags

TypeWhat it isWhen to use
LightweightA simple name pointing at a commitQuick personal bookmarks
AnnotatedA full object with tagger, date and messageReleases you share
 
$ git tag v1.0.0-test
$ git tag -a v1.0.0 -m "First stable release"

Prefer annotated tags for anything public.

20.3 Working with tags

CommandWhat it does
git tagList tags
git tag -a v1.1.0 <hash> -m "msg"Tag an older commit
git show v1.0.0See the tag and its commit
git switch --detach v1.0.0Look at the project at that version
git tag -d v1.0.0-testDelete a local tag

20.4 Sharing tags

git push does not send tags by default. You send them on purpose.

$ git push origin v1.0.0
$ git push origin --tags
$ git push origin --delete v1.0.0

20.5 Version numbers

Most projects follow semantic versioning: MAJOR.MINOR.PATCH.

PartIncrease whenExample
MAJORYou make a breaking change1.4.2 to 2.0.0
MINORYou add a feature that stays compatible1.4.2 to 1.5.0
PATCHYou fix a bug1.4.2 to 1.4.3

On GitHub, a tag can become a Release, a page with notes and downloadable files for that version.

20.6 Common mistakes

  • Forgetting to push tags. Teammates cannot see them.
  • Moving a published tag. Others may already depend on it. Create a new tag instead.
  • Using lightweight tags for releases. They carry no message or date.
Quick recap
  • A tag names one commit permanently.
  • Use annotated tags (-a) for releases.
  • Push tags explicitly with git push origin <tag> or --tags.
  • Semantic versioning uses MAJOR.MINOR.PATCH.

Practice exercise
  • Create an annotated tag v0.1.0 on your latest commit.
  • Run git show v0.1.0 and read the output.
  • Make another commit, then confirm the tag still points to the older commit.
