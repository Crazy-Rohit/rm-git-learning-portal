What is version control?

Version control records every change made to a set of files, so you can go back to any earlier state, see who changed what, and work with other people without overwriting their work.

1.1 The problem it solves

Everyone has seen a folder like this:

report.docx
report_final.docx
report_final_v2.docx
report_final_v2_REALLY_FINAL.docx
report_final_v2_REALLY_FINAL_ravi_edits.docx

Nobody knows which file is the latest, what changed between them, or who changed it. Now imagine 500 source files and 10 developers. Three things go wrong:

  • Lost work. Someone overwrites a file and the earlier version is gone for good.
  • No history. A bug appears and nobody can tell which change caused it.
  • Collision. Two people edit the same file and one person's changes silently disappear.

A version control system (VCS) fixes all three. It keeps every version, labels each change with its author, date and reason, and helps merge work from many people.

1.2 Analogy: a time machine for your project

Think of a video game with save points. Before a hard level you save. If you fail, you reload and try again. Each commit in Git is a save point with a name and a note, and you can return to any save point whenever you like.

It is also like Google Docs version history, with more control: you decide when a save point is made, you write a note for it, and it works for any type of file.

1.3 Three generations of version control

GenerationHow it worksExamplesMain weakness
LocalThe version database lives on one computerRCSNo collaboration; a disk failure loses everything
CentralizedOne server holds the history; developers check files out of itCVS, SubversionIf the server is down nobody can save history; it is a single point of failure
DistributedEvery developer has a full copy of the whole historyGit, MercurialA few more concepts to learn at the start

When you clone a Git repository you get the complete history, not just the latest files. That is why most Git commands work without internet.

1.4 Key terms you will see everywhere

TermPlain meaning
Repository (repo)A project folder together with its full recorded history
CommitOne saved snapshot of your project, with a message and an author
BranchA separate line of work that does not disturb the main line
MergeCombining the work of two branches into one
RemoteA copy of the repository on another machine or server, such as GitHub
CloneDownloading a full copy of a remote repository
Note

Do not memorise these now. Each term gets its own chapter with examples.

1.5 Why teams cannot work without it

  • Collaboration: ten people can work on one codebase at the same time.
  • Traceability: every line can be traced to a person, a date and a reason.
  • Safety: a mistake is never permanent, because you can return to an earlier commit.
  • Experimentation: try a risky idea on a branch and throw it away if it fails.
  • Release management: mark exactly which version went to production.

1.6 Common mistakes

Warning

Copying folders as backups. A folder copy has no notes, no author and no way to merge. Use commits instead.

  • Thinking version control is only for code. It works for documents, configuration and notebooks too. Very large binary files need extra tools (Git LFS, in Part 5).
  • Waiting too long to start. Track the project from day one, not after a problem appears.
Quick recap
  • Version control records every change to your files.
  • Local, centralized and distributed are the three generations.
  • Git is distributed: every clone holds the full history.
  • A commit is a save point; a repository is the project plus its history.
Practice exercise
  • Think of a project from the past year and write down three moments when you wished you could go back.
  • For each moment, note what information (who, when, why) would have helped most.
  • Keep the list. Git records exactly that information, as Part 2 shows.
