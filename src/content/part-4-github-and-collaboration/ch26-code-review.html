Code review

Review is where teammates catch bugs, share knowledge and keep quality high, and a kind, clear style makes it work.

26.1 Why review code

Another pair of eyes finds problems the author no longer sees. Review also spreads knowledge across the team, so no part of the project is understood by only one person.

26.2 How a review works on GitHub

Open Files changed. Hover over a line, select the + button and leave a comment. When you finish, choose Review changes and pick one of three options.

ChoiceMeaning
CommentGeneral feedback without approving or blocking
ApproveThe change is good to merge
Request changesThe author must address issues before merging

26.3 Suggested changes

Inside a comment, choose the Add a suggestion button. GitHub inserts a special block that you edit to hold the replacement text, for example:

total = price * quantity

The author accepts it with Commit suggestion, and GitHub makes the commit for them. Suggestions are ideal for typos and small fixes.

26.4 What to look for

AreaQuestions
CorrectnessDoes it do what the description says? Are edge cases handled?
TestsAre there tests, and do they pass?
ReadabilityAre names clear? Is anything too complicated?
SecurityAny secrets, unsafe input or risky permissions?
ScopeIs the change focused, or did unrelated edits slip in?

26.5 Writing helpful comments

  • Comment on the code, not the person: "This loop can skip the last item" rather than "You made a mistake".
  • Explain why, and offer an alternative when you can.
  • Label small preferences, for example "nit:" for style points that need not block merging.
  • Praise good work. It is part of a review too.

26.6 Receiving feedback

  • Assume good intent. Reviewers want the project to succeed.
  • Reply to every comment, even if only to say "Done".
  • Disagree politely with reasons, and ask questions if something is unclear.
  • Push fixes as new commits, then click Resolve conversation once addressed.

26.7 Requesting a review

Use the Reviewers panel on the right of the pull request. A file called CODEOWNERS (Chapter 33) can add the right reviewers automatically.

26.8 Common mistakes

  • Approving without reading. A rubber stamp helps nobody.
  • Rewriting the author's design in comments. Discuss big design questions before the code is written.
  • Waiting days to review. Slow feedback blocks the team. Aim to respond within a working day.
Quick recap
  • Reviews catch bugs and share knowledge.
  • Choose Comment, Approve or Request changes when you finish.
  • Be specific, kind and focused on the code.
  • Reply to comments and resolve conversations as you fix them.
Check yourself

1. Which review choice blocks a pull request until the author responds?

Practice exercise
  • Open a pull request in a practice repository with a friend, and leave three comments, one of them a suggestion.
  • Apply a suggestion as the author and resolve the conversation.
