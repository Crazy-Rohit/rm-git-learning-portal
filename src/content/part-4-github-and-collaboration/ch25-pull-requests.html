Pull requests

A pull request asks the project to take your branch, and it is where discussion, review and automatic checks happen before merging.

25.1 What a pull request is

A pull request (PR) is a proposal to merge one branch into another. It is a page on GitHub that shows the changes, hosts the discussion and runs automatic checks. Even on your own project, PRs are a good habit because they record why a change was made.

25.2 Opening a pull request

$ git switch -c fix-typo
$ git add README.md
$ git commit -m "Fix typo in installation steps"
$ git push -u origin fix-typo
remote: Create a pull request for 'fix-typo' on GitHub by visiting:
remote:   https://github.com/your-username/hello-git/pull/new/fix-typo

GitHub shows a Compare and pull request button. On the form, write:

  • A clear title, like a good commit message.
  • A description of what changed and why, with screenshots if the change is visual.
  • Closing keywords such as Closes #12, which automatically close issue 12 when the PR merges.
  • Reviewers and assignees, if your team uses them.

25.3 Draft pull requests

Choose Create draft pull request when the work is not ready. A draft cannot be merged. It tells people you want early feedback, not a final review.

25.4 Reading a pull request page

25.5 Three ways to merge

OptionResultBest for
Merge commitKeeps all commits and adds a merge commitPreserving full history
Squash and mergeCombines the branch into one commitTidy main with one commit per change
Rebase and mergeReplays commits on top, no merge commitA straight history with every commit kept

Repository owners can allow only the styles they prefer.

25.6 After the merge

$ git switch main
$ git pull
$ git branch -d fix-typo

GitHub offers a Delete branch button after merging. Use it to keep the branch list short.

25.7 Pull request templates

A file named .github/pull_request_template.md fills each new PR with a checklist, which helps authors remember tests and documentation.

## What does this change?

## How was it tested?

- [ ] Tests added or updated
- [ ] Documentation updated

25.8 Common mistakes

  • Huge pull requests. Reviewers skim them. Keep PRs small and focused.
  • No description. Explain the why, not just the what.
  • Pushing more commits after approval without telling anyone. New commits usually require a fresh review.
Quick recap
  • A pull request proposes merging a branch and hosts the review.
  • Write a clear title and description, and link issues with Closes #n.
  • Use draft PRs for early feedback.
  • Merge commit, squash and rebase are the three merge styles.

Practice exercise
  • Create a branch, push it, and open a pull request in your own repository.
  • Merge it with Squash and merge, then delete the branch.
  • Run git pull locally to bring the merged result into main.
