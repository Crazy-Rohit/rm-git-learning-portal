Team best practices

Good habits make a repository pleasant for everyone, and most of them take only a few seconds.

40.1 Commits

  • Commit small and often; each commit does one thing.
  • Write messages in the imperative: "Add", "Fix", "Remove".
  • Never commit secrets, generated files or large binaries.
  • Make sure the project builds and the tests pass at every commit when you can.

40.2 Conventional commits

Many teams add a short type prefix, which helps tools generate change logs and version numbers.

PrefixUse forExample
featA new featurefeat: add password reset
fixA bug fixfix: handle empty cart
docsDocumentation onlydocs: explain install steps
refactorCode restructuring without behaviour changerefactor: split payment module
testAdding or fixing teststest: cover login errors
choreTooling and maintenancechore: update dependencies

40.3 Branches

  • Name branches by purpose: feature/search, fix/login-timeout.
  • Keep them short-lived and delete them after merging.
  • Update from main regularly to avoid giant conflicts.

40.4 Pull requests

  • Keep them small. A few hundred changed lines at most is a good target.
  • Explain what and why, and link the issue.
  • Run the tests yourself before asking for review.
  • Review your own pull request first; you will catch things.

40.5 Reviews

  • Respond within a working day.
  • Be kind, specific and constructive (Chapter 26).
  • Authors fix; reviewers do not push to someone else's branch without asking.

40.6 Repository settings

  • Protect main and require reviews and checks (Chapter 33).
  • Keep a clear README, CONTRIBUTING.md and .gitignore.
  • Turn on Dependabot and secret scanning (Chapter 38).
  • Use one line-ending policy through .gitattributes.
# .gitattributes
* text=auto
*.sh text eol=lf

40.8 Common mistakes

  • Different habits for each person. Write the rules down once.
  • Huge, rare merges. Integrate small and often.
  • Skipping reviews under pressure. That is exactly when bugs slip in.
Quick recap
  • Small, clear commits and focused pull requests keep history readable.
  • Conventional commit prefixes help automation.
  • Protect main, review quickly and keep documentation current.
  • A simple onboarding path gets newcomers productive fast.
