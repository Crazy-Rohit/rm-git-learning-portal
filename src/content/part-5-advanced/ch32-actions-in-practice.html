Actions in practice

Matrices, secrets, caching and schedules turn a simple workflow into a dependable pipeline.

32.1 Test on several versions: matrix

A matrix runs the same job many times with different values.

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.11", "3.12", "3.13"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
      - run: pytest

Three parallel jobs appear, one per version.

32.2 Secrets

Never write passwords or API keys in a workflow file. Store them under Settings, then Secrets and variables, then Actions, and read them in the workflow.

steps:
  - run: ./deploy.sh
    env:
      API_TOKEN: ${{ secrets.API_TOKEN }}

GitHub hides secret values in the logs. Secrets are not passed to workflows triggered from forks, which protects you from malicious pull requests.

32.3 Caching dependencies

Many setup actions can cache downloads and make runs faster.

- uses: actions/setup-python@v5
  with:
    python-version: "3.12"
    cache: pip

32.4 Other triggers

TriggerStarts the workflow when...
pushCommits are pushed
pull_requestA pull request is opened or updated
scheduleA cron time arrives
workflow_dispatchSomeone clicks Run workflow
releaseA release is published
 
on:
  schedule:
    - cron: "0 3 * * 1"
  workflow_dispatch:

That runs every Monday at 03:00 UTC, and also gives you a manual Run workflow button.

32.5 Artifacts: keep the output

- uses: actions/upload-artifact@v4
  with:
    name: test-report
    path: reports/

Artifacts are files saved with a run, such as test reports or built packages, which you can download from the run page.

32.6 Deploying to GitHub Pages

permissions:
  contents: read
  pages: write
  id-token: write

The permissions block gives the workflow's built-in token only what it needs. Combined with the official Pages actions, it publishes your site after each push to main.

32.7 Writing safe workflows

  • Give the token the least permissions with a permissions: block.
  • Treat pull requests from forks as untrusted. Do not run their code with access to secrets.
  • Trust actions from verified creators, and pin important third-party actions to a full commit hash.

32.8 Common mistakes

  • Printing secrets in logs. Even masked values can leak when transformed.
  • Using pull_request_target carelessly. It can expose secrets to untrusted code.
  • Very slow workflows. Cache, run jobs in parallel and test only what changed.
Quick recap
  • A matrix repeats a job across versions or systems.
  • Store credentials as secrets, never in the YAML.
  • Triggers include push, pull request, schedule and manual runs.
  • Limit permissions and treat fork pull requests as untrusted.
