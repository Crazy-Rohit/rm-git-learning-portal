Security: secrets, Dependabot and signed commits

One leaked password can undo a project, so build safe habits and let GitHub's automatic tools watch for you.

38.1 Rule one: secrets do not belong in Git

Passwords, API keys, tokens and private keys must never be committed. Even if you delete the file later, the secret remains in the history, and public repositories are scanned by bots within minutes.

38.2 If you leak a secret

Revoking comes first because anyone may already have copied the secret. Cleaning history is a second, optional step.

38.3 Keeping secrets out

  • Put them in a .env file that is listed in .gitignore, and commit a .env.example with fake values.
  • Use your platform's secret store: GitHub Actions secrets, a cloud key vault or a password manager.
  • Turn on secret scanning and push protection in your repository's security settings, which block pushes that contain recognised secrets.
  • Add a pre-commit hook that scans for secrets (Chapter 34).

38.4 Dependabot

Dependabot watches your dependencies.

FeatureWhat it does
Dependabot alertsWarns when a dependency has a known vulnerability
Dependabot security updatesOpens a pull request with the fix
Dependabot version updatesOpens regular pull requests to keep dependencies current
 
# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: "pip"
    directory: "/"
    schedule:
      interval: "weekly"

38.5 Code scanning

Code scanning with CodeQL analyses your source for common vulnerability patterns and reports them on pull requests. It is free for public repositories and available for private ones on some plans.

38.6 Protect your account

  • Use a strong, unique password in a password manager.
  • Turn on two-factor authentication. GitHub requires it for people who contribute code.
  • Consider passkeys or hardware security keys.
  • Review Settings, then Sessions and SSH keys now and then, and remove what you do not recognise.

38.7 Signed commits

Anyone can set any name and email in Git, so a commit's author is not proof of identity. A signature proves that the commit came from the holder of a key. GitHub marks such commits Verified. Git can sign with an SSH key, which you may already have from Chapter 23.

$ git config --global gpg.format ssh
$ git config --global user.signingkey ~/.ssh/id_ed25519.pub
$ git config --global commit.gpgsign true

Add the same public key in GitHub under SSH and GPG keys, choosing the type Signing key.

38.8 Report vulnerabilities properly

A SECURITY.md file tells visitors how to report a problem privately. GitHub also offers private vulnerability reporting, so researchers do not post exploits in public issues.

38.9 Common mistakes

  • Thinking a private repository is safe for secrets. Access changes, repositories get forked and leaked.
  • Deleting the file and calling it fixed. The history still has it.
  • Ignoring Dependabot pull requests. Old, vulnerable dependencies are a common way in.
Quick recap
  • Never commit secrets; use .gitignore, secret stores and push protection.
  • If one leaks, revoke it first, then clean history.
  • Dependabot and code scanning find vulnerable dependencies and code.
  • Use two-factor authentication and sign your commits.
Check yourself

1. You pushed an API key by mistake. What is the FIRST step?

The key may already be copied, so make it useless immediately.

Practice exercise
  • Create .env.example and add .env to .gitignore in a practice project.
  • Add a dependabot.yml file and enable secret scanning in the repository settings.
  • Set up SSH commit signing and look for the Verified badge on GitHub.
